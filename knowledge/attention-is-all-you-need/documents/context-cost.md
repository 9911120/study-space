# 긴 문맥 — 계산·메모리·품질

Self-Attention의 점수표를 직접 만들면 길이 n인 입력에서 `[n, n]`개의 점수를 갖습니다. 단순 구현에서는 토큰 길이를 두 배로 늘릴 때 이 표의 칸 수가 네 배가 됩니다.

## 모델 전체가 항상 네 배 느려지나요?

그렇지는 않습니다. 모델에는 Q·K·V 투영과 FFN 등 다른 연산이 있고, 실제 커널·배치·하드웨어·캐시가 시간에 영향을 줍니다. 프리필과 디코드는 처리하는 Query 수와 실행 특성도 다릅니다. 점수표의 크기 변화와 서비스 전체 지연 시간을 구별해야 합니다.

## FlashAttention과 연결합니다

FlashAttention은 주된 아이디어로 메모리 이동을 줄이고, 전체 점수표를 GPU의 큰 메모리에 그대로 물질화하지 않는 방식의 정확한 어텐션 계산을 다룹니다. 어텐션을 무조건 다른 근사 수식으로 바꾸는 것과는 다릅니다. 또한 구현 효율이 좋아진다고 dense attention의 모든 계산 의존성이 없어지는 것은 아닙니다.

## 길이 한도와 품질도 다릅니다

모델이 어떤 길이의 입력을 받을 수 있다는 사실만으로 그 안의 모든 정보가 같은 수준으로 활용된다고 보장할 수 없습니다. 프롬프트 위치, 과제, 모델에 따라 결과가 달라집니다. 실제 앱에서는 문맥 길이와 정답률·지연·메모리를 함께 측정하는 것이 좋습니다.

## 확인합니다

긴 문서를 넣었을 때 ‘입력이 허용됐다’, ‘정보를 잘 찾았다’, ‘빠르게 끝났다’가 서로 다른 주장인 이유를 설명해 보십시오.
