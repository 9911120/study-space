# 프리필 — 주어진 입력 처리

디코더 전용 LLM에 프롬프트를 전달하면 아직 아무 출력도 생성하지 않았더라도 입력 토큰들은 모두 알고 있습니다. 프리필은 이 알려진 입력을 모델에 통과시키는 단계입니다.

## 병렬 처리와 마스크가 함께 있습니다

프롬프트의 여러 위치를 한 층 안에서 함께 계산할 수 있지만, 인과적 모델의 각 위치는 미래 위치를 보지 못합니다. 병렬화가 causal mask를 없앤다는 뜻은 아닙니다. 층 사이에는 여전히 계산 순서가 있습니다.

일반적인 자기회귀 실행에서는 마지막 입력 위치의 최종 표현으로 첫 번째 새 토큰의 분포를 계산합니다. KV 캐시를 사용하는 구현은 이 과정에서 이후 생성에 필요한 과거 위치의 K와 V도 마련합니다.

## 입력 길이와 첫 토큰 시간

긴 문서는 처리할 토큰이 많고, 위치 간 정보를 모으는 계산도 커집니다. 그래서 프리필은 입력 길이의 영향을 받습니다. 다만 실제 서비스의 첫 토큰 시간에는 대기열, 토큰화, 전송, 캐시 적중 여부 등도 섞입니다. 지연을 전부 모델 수식 하나로 설명하면 안 됩니다.

## 요청 사이 재사용은 별도 조건입니다

하나의 요청 안에서 KV를 재사용하는 것과, 다른 요청의 같은 접두사를 재사용하는 prefix caching은 구별합니다. 후자는 모델과 토큰 접두사, 실행 상태 등의 재사용 조건이 맞고 서빙 엔진이 지원해야 합니다. 의미만 비슷한 두 프롬프트가 같은 캐시를 쓴다고 가정하지 않습니다.

## 확인합니다

프롬프트 처리가 병렬화될 수 있는데도 첫 토큰 지연이 입력 길이에 영향을 받는 이유를 설명해 보십시오.
